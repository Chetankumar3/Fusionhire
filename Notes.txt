Edge cases:
- I assume that all emails are from non recycling providers (Google, Microsoft, unlike Yahoo). I acknowledge that phone numebrs are recycled. But, due to time constraints I ignore that.
- Experience date format in source files.
Date format assumptions. These are rare formats, but handled using assumptions.
XX-XX-XXXX assumed to be DD-MM-YYYY
XXXX-XX-XX assumed to be YYYY-MM-DD [ISO 8601]
XX-XXXX-XX assumed to be DD-YYYY-MM

Other points:
- OpenResume over pyresparser: I decoupled extraction and transformation. Due to which I could use best open source Resume parser OpenResume and directly use the generated jsons in my python transfromation engine.
pyresparser can become problematic in merging data in blocks. For example, it may find "Software Engineer" and "Google," but its not highly reliable linking them together into a single block, also it is not perfectly deterministicm, which contradicts the PS constraints.
- Archives collection instead of hard delete.
- procurement date while ingestion.
- Non-determinism in candidate_id

Architectural Decision:
- Simple script files instead of always running servers. Companies rarely require always running resources for managing canidate profiles. One command = all the work, MongoDB for persistence.
- Decoupled Ingestion: Decoupling data ingestion makes it drastically easier to expand to multiple sources. The core transformation engine does not need to be modified; instead, any new source simply requires its own lightweight conversion tool to generate a standardized JSON file for the core engine to consume.
- Database as a File (Mongita): To group candidates using our match keys, I needed the ability to query arrays (e.g., finding all candidates whose email list contains a specific email, or phone list contains a specific number). To offload these complex queries, I utilized MongoDB approach. However, to completely eliminate setup friction for the reviewer, I used Mongita—a lightweight, embedded database. This provides the NoSQL query power we need while keeping the application zero-dependency and highly extensible for a production environment, we just have to spinup the mongoDB instance and change env.
This also decouples the 'merge_engine' and 'projector'.
